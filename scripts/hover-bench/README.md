# Windows hover benchmark

Run on a disposable Windows desktop with WebView2, Python 3 (the Windows `py` launcher), Node and the project's npm dependencies. The benchmark moves the Windows cursor and clicks the actual Settings button. Use a fresh Windows account or Windows Sandbox. Keep the existing desktop and profile available for ordinary work.

Place each portable EXE next to its workflow-generated `SHA256.txt`. Use the Windows Settings display scale to set the disposable desktop to 100%, then run the pair in PowerShell.

```powershell
$env:MUSIC_ISLAND_DISPOSABLE_DESKTOP = '1'
./scripts/hover-bench/compare.ps1 -BaselineExe C:\QA\baseline\music-island.exe -CandidateExe C:\QA\candidate\music-island.exe -Output C:\QA\pair-100 -Dpi 96
```

Repeat after switching Windows to 150%, using a new output directory and `-Dpi 144`. The helper reads the DPI of the actual overlay HWND and the refresh rate of its monitor. The workflow's `hover_benchmark` option runs the approved 3.2.2 baseline and candidate on one hosted runner at its measured scale. It also attempts to select 150% through Windows Display Settings. The second pair requires a measured 144 DPI. If the virtual display does not offer that scale, the `hover-150-results` artifact records the reason.

Each run includes the first hover after startup, the next one after five minutes collapsed, and 198 further hovers. In the default `models` scenario both binaries download the same 1.55 GB Whisper Turbo model. The third and fourth gestures start when the application reports download and SHA-256 verification respectively. For the fifth gesture the application unloads the model and begins a fresh load during the normal hover dwell. The first physical click runs independently of these operations. Per-span results include only trials whose acceptance-to-first-targetable-frame interval intersects the measured native workload. The report records each intended phase and fails coverage if an actual phase falls between all gestures. Use `-Scenario idle` to collect an idle-only pair.

For a candidate-only run with a newly published model, set `MUSIC_ISLAND_HOVER_MODEL` to its catalog ID and run `node scripts/hover-bench/run.mjs C:\QA\candidate\music-island.exe $candidateSha C:\QA\new-model 200 auto 300 models`. Its isolated Settings WebView invokes the application's catalog download, checksum and cold-load paths.

For the dedicated public model smoke, select `gigaam_public_smoke` in the Windows build workflow after the model assets are public. The equivalent command on the disposable test desktop is `node scripts/hover-bench/run.mjs C:\QA\candidate\music-island.exe $candidateSha C:\QA\public-download public-models`. This mode uses the hidden owned Settings WebView and leaves the system pointer alone. It checks each file's native verification completion, rescans the catalog, checks the loaded ID, unloads and removes the installed pack, then repeats for the second ID. The checkout must contain the pinned pack catalog used to build the candidate.

Run `./scripts/hover-bench/streaming.ps1 -BaselineExe C:\QA\baseline\music-island.exe -CandidateExe C:\QA\candidate\music-island.exe -Output C:\QA\streaming` on a disposable desktop with an existing private VB-CABLE endpoint pair. A local English Windows voice generates the WAV. The repository's audio helper renders solely to that cable. The application must acknowledge the corresponding exact capture endpoint, load the CPU streaming model and emit a nonempty live preview from the fixture. Each hover is matched against the application's ready streaming state. The report records preview counts and timestamps. It omits audio and transcript content. The hosted workflow saves an explicit unavailable result when it cannot find that cable. For live GPU lens QA, enable it in Appearance in the disposable profile and verify the native visual handoff described in the QA guide.

The runner refuses an existing Music Island profile or process. It starts the supplied EXE with separate AppData and WebView2 folders and discovers the debugging endpoint from the new WebView profile. It moves the cursor to the overlay edge and attempts a single OS click at the centre of the first hittable Settings button. A successful trial requires both a trusted DOM click and a visible native Settings window owned by the benchmark process. Coordinates go through the actual window client rectangle, including monitor DPI. The helper skips clicks landing on another window. The runner then closes the owned settings window and moves the pointer off the island.

`report.json` is written after every trial. It includes the OS pointer movement, the first WebView edge contact, configured-gesture acceptance, the first sampled visible and hittable frames, native click injection, trusted click reception and the Settings action outcome. Timestamps use Unix epoch milliseconds. `peekCommit` is a DOM update, and requestAnimationFrame plus computed visibility measures a render opportunity. Measuring physical scanout requires an external display trace. The older build uses the first `opening` DOM commit as its acceptance proxy unless built with the two measurement markers.

Review p99, maximum, every trial over two measured display periods and every missed first click. For the pair, compare the same OS edge contact or the same opening DOM commit against the first targetable frame. The candidate also records the earlier gesture acceptance marker. Report injection and input-delivery latency separately. The five-minute collapsed interval samples the owned process tree every 30 seconds and requires the same native and WebView2 processes throughout. A changed process set, missing counters or a candidate above 1% of total logical-processor capacity fails the CPU check. The report also gives the percentage of one logical CPU. The debugger remains attached during this interval with frame sampling suspended.
